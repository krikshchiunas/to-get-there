# Стейджинг и выкатка миграций

Как изменение схемы доходит от ветки до продакшена и что делать, если
что-то пошло не так. Коротко: **сначала с нуля в CI, потом стейджинг, потом
прод; только вперёд; ломающее — в два шага.**

## Окружения

| Где | База | Приложение | Зачем |
|---|---|---|---|
| Локально | `supabase start` (Docker) или моки (`NEXT_PUBLIC_USE_MOCKS=true`) | `npm run dev` | разработка |
| CI | свежая локальная Supabase на каждый коммит | `next build` против неё | все миграции с нуля, pgTAP, нагрузочный прогон, E2E со входом |
| Стейджинг | отдельный проект Supabase `to-get-there-staging` | Vercel Preview | миграция на копии с живыми настройками Auth, Storage и cron |
| Продакшен | проект `to-get-there` (eu-central-1) | Vercel Production, `main` | пользователи |

CI ловит сломанную миграцию и дыру в правах, но не всё: настройки Auth,
почта, cron, расширения и объём данных у прода свои. Для этого стейджинг.

## Завести стейджинг (один раз, руками)

Проект Supabase и переменные Vercel создаёт владелец аккаунта — у
автоматизации на это прав нет.

1. **Supabase → New project**: `to-get-there-staging`, регион
   `eu-central-1` (как прод, иначе задержки и юрисдикция данных другие),
   тот же тариф.
2. Локально:
   ```bash
   supabase link --project-ref <ref-стейджинга>
   supabase db push
   ```
   История у нового проекта пустая, поэтому `db push` накатит
   `0001…` по порядку с теми же номерами, что в репозитории.
3. **Сид — только демо**: `psql "$STAGING_DB_URL" -f supabase/seed.sql`.
   Данные прода на стейджинг не копируются (DSGVO: у стейджинга нет
   правового основания хранить данные пользователей).
4. **Authentication → URL Configuration**: Site URL — адрес preview
   Vercel (`https://to-get-there-git-main-<team>.vercel.app`), Redirect
   URLs — `https://*-<team>.vercel.app/**`.
5. **Authentication → Email Templates**: те же шаблоны, что на проде
   (см. «Сделать руками» в `docs/SECURITY.md`), свой SMTP или встроенная
   почта — письма уходят только участникам команды, для стейджинга этого
   хватает.
6. **Vercel → Settings → Environment Variables → Preview**:
   `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` стейджинга,
   `NEXT_PUBLIC_USE_MOCKS=false`. Production-переменные не трогать.

## Правила миграций

- **Только вперёд.** Применённый файл не правится никогда. Ошибка в
  миграции исправляется следующей миграцией.
- **Номер — следующий по порядку**, имя — что делает:
  `0042_<что_меняется>.sql`. Один смысл — одна миграция.
- **Повторный запуск безопасен**, где это возможно: `if not exists`,
  `create or replace`, `drop … if exists`.
- **Права вместе со схемой.** Новая таблица — в той же миграции RLS,
  `revoke` у `anon`/`authenticated` и только нужные `grant`. Новая
  функция — `set search_path = ''`, `revoke … from public`.
- **Тесты в том же PR.** Новое правило доступа — проверка в
  `supabase/tests/database`; новый тяжёлый запрос — строка в
  `supabase/perf/queries.sql` с бюджетом.
- **Ломающее — в два шага (expand → contract).** Переименовать или
  удалить колонку, которую читает приложение:
  1. миграция добавляет новое (колонку, таблицу, функцию) и переносит
     данные; старое остаётся;
  2. выкатывается приложение, которое читает и пишет только новое;
  3. следующая миграция, уже после выкатки, удаляет старое.

  Так между миграцией и деплоем нет окна, когда работающая версия
  приложения ходит в несуществующую колонку.

  *Разбор:* 0040 (интересы в отдельной таблице) сделана одним шагом —
  колонки удалены той же миграцией, а новая версия приложения выехала
  через несколько минут. Пока Vercel собирал её, профиль на проде отдавал
  ошибку. На нескольких пользователях это минуты, на настоящей аудитории —
  инцидент. Отсюда правило выше.

## Порядок выкатки

1. **PR.** CI накатывает все миграции на чистую базу, гоняет pgTAP,
   `supabase db lint`, нагрузочный прогон и E2E со входом. Красное — не
   сливается (защита ветки `main`, см. `docs/ROADMAP.md`).
2. **Стейджинг.**
   ```bash
   supabase link --project-ref <ref-стейджинга>
   supabase db push --dry-run   # что именно применится
   supabase db push
   ```
   Затем: Supabase → Advisors (security и performance — ноль новых
   замечаний), открыть preview-деплой и пройти изменённый сценарий.
3. **Прод — миграция.** В окно с наименьшей нагрузкой (будни, утро по
   Берлину). Перед ломающей или долгой миграцией — ручной бэкап
   (Database → Backups) или `pg_dump` схемы и затронутых таблиц.
4. **Прод — приложение.** Слияние в `main`, Vercel выкатывает сам. Для
   contract-шага — только после того, как предыдущий деплой отработал
   сутки без ошибок.
5. **Проверка.** `GET /api/health` → `{"status":"ok","database":"ok"}`,
   Advisors, логи Supabase (API и Postgres) за первые 15 минут.

### История миграций на проде

До сих пор прод мигрировался через `apply_migration` (Supabase MCP):
версии в `supabase_migrations.schema_migrations` — метки времени
(`20261019071201` …), а не `0001` … как у файлов. **`supabase db push` на
проде без подготовки попробует накатить всё заново.** Перед первым
`db push` на прод:

```bash
supabase link --project-ref ntcksmrytrknwhyupzot
supabase migration list                      # слева файлы, справа прод
supabase migration repair --status reverted 20261019071201 20261019071221   # … все метки
supabase migration repair --status applied 0001 0002                        # … все номера
supabase migration list                      # колонки совпали
```

`repair` меняет только журнал, не схему. Пока это не сделано, на прод
применять тем же способом, что раньше, — по одному файлу, с тем же именем.

## Если пошло не так

- **Миграция упала** — Postgres откатывает её целиком (каждый файл — одна
  транзакция). Чинить и выкатывать следующим номером.
- **Миграция прошла, приложение сломалось** — откатить деплой (Vercel →
  Deployments → Promote предыдущий). Схема при expand-шаге совместима со
  старой версией — для этого шаги и разделены.
- **Потеряны данные** — Database → Backups (ежедневные; на Pro — PITR до
  секунды). Восстановление — в новый проект, нужное переносится выборочно:
  восстановление поверх прода откатит и чужие изменения.
- **Записать** что случилось, во сколько и почему — в PR с исправлением.

## Чек-лист миграции

- [ ] Номер следующий, файл не переименовывает и не правит старые.
- [ ] RLS, `revoke`, `grant`, `search_path` на месте.
- [ ] pgTAP на новое правило, строка в `supabase/perf/queries.sql` на новый запрос.
- [ ] Ломающее разбито на expand и contract.
- [ ] `lib/database.types.ts` обновлён.
- [ ] Стейджинг: `db push`, Advisors чистые, сценарий пройден руками.
- [ ] Прод: бэкап перед долгим или ломающим, health и логи после.
