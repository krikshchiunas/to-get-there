# Вход и аккаунт

Как устроены регистрация, вход, сессии, восстановление пароля и что из
этого держит база. Короткая версия: **личность — `auth.users.id` из Supabase
Auth, права — RLS через `private.current_user_id()`, и база признаёт только
живую сессию.** Приложение объясняет и направляет, но не решает за базу.

## Модель

| Что | Где | Кто пишет |
|---|---|---|
| Аккаунт: почта, хеш пароля, подтверждение, сессии | `auth.users`, `auth.sessions` (Supabase Auth) | только Auth |
| Профиль: ник, аватар, приватность | `public.users`, `user_tags`, `user_settings` | владелец через RLS; создаёт триггер |
| Вуз | `public.users.university_id` | только проверяемый путь: домен почты или `email_allowlist` |
| Кто может создать аккаунт | `private.registration_policy` | только миграции |

- `users.id` — свой uuid (решение этапа 4, `docs/DATABASE.md`), а связь с
  аккаунтом — `users.auth_user_id` → `auth.users.id`, `unique`, каскадное
  удаление. Канонический идентификатор человека — `auth.users.id`: из него
  и только из него (`sub` в проверенном JWT) база выводит `users.id`.
- Ни один запрос не принимает id пользователя от клиента как «кто я»: все
  политики берут его из `private.current_user_id()`.
- Пароли хранит Supabase Auth (bcrypt). Приложение их не хранит, не
  логирует и обратно в браузер не отдаёт — даже в состоянии формы.

## Регистрация

```
форма /auth/signup ── проверка полей (lib/auth/validation.ts, в браузере и на сервере)
        │
server action signUp ── public.signup_allowed(email)  — подсказка: «с этой почтой сейчас нельзя»
        │
Supabase Auth /signup ── insert auth.users
        │                    └─ триггер on_auth_user_created → private.create_profile()
        │                         ├─ private.signup_allowed() — отказ = нет аккаунта вовсе
        │                         ├─ вуз: email_allowlist или домен из universities, иначе NULL
        │                         └─ ник user + 8 hex, профиль + user_tags + user_settings
        │                       (одна транзакция: аккаунта без профиля не бывает)
        ▼
письмо подтверждения ── /auth/check-email (почта в httpOnly-cookie, не в адресе)
```

- **Поля:** почта, пароль, пароль ещё раз, флажок «Мне есть 16, я принимаю
  условия и правила сообщества». Флажок проверяет сервер; редакция условий
  (`LEGAL_REVISION`) и время согласия записываются в `user_metadata`.
- **Пароль:** не короче 8 символов и не длиннее 72 байт (bcrypt). Без
  требований «заглавная и цифра» — NIST SP 800-63B. Тот же минимум стоит в
  самом Auth (`supabase/config.toml`, на проде — панель), иначе прямой
  вызов API принял бы 6 символов. Утёкшие пароли отсекает проверка Supabase
  (платный тариф; ошибка `weak_password` с причиной `pwned` показывается
  отдельным текстом).
- **Ник случайный** (`user3fa91c0d`). Раньше он брался из почты:
  `ivan.petrov.1999@gmail.com` давал публичный `/u/ivan.petrov.1999` — утечка
  адреса и способ проверить, зарегистрирован ли человек.
- **Повторная регистрация** с занятой почтой отвечает так же, как с новой:
  «Проверь почту». Пароль существующего аккаунта не меняется.

## Подтверждение почты

Письмо ведёт на один из двух адресов:

| Ссылка | Работает | Когда |
|---|---|---|
| `/auth/callback?code=…` (PKCE, шаблон по умолчанию) | в том же браузере | всегда |
| `/auth/confirm?token_hash=…&type=signup` | на любом устройстве | если шаблон письма изменён (ниже) |

Состояния:

| Что произошло | Что видит человек |
|---|---|
| ссылка сработала | сразу в приложении (или на экране, ради которого входил: `next`) |
| ссылка открыта в другом браузере (PKCE) | «Почта подтверждена. Теперь войди» — Auth подтверждает почту до обмена кода |
| ссылка уже использована, человек вошёл | просто в приложении |
| ссылка устарела или использована, не вошёл | вход с объяснением |
| вход до подтверждения | «Почта ещё не подтверждена» и ссылка «Отправить письмо ещё раз» |
| «Отправить письмо ещё раз» | один и тот же ответ для любого адреса; кнопка ждёт минуту (лимит Auth) |

Auth не различает «устарела» и «неверная» (`otp_expired` в обоих случаях),
поэтому экран тоже не различает.

## Вход

`/auth/login` (и `/login` — временный редирект). Почта и пароль, «Показать
пароль», `autocomplete="email"`/`"current-password"`. Ошибка — одна на оба
поля: «Неверная почта или пароль» — и для неизвестной почты тоже.

**Куда вернуться.** Middleware отправляет на `/auth/login?next=<путь>`.
`next` проходит `safeNext()` (`lib/safe-next.ts`): только путь внутри сайта,
после нормализации URL, не `//`, не `\`, не управляющие символы, не экраны
входа. `https://evil.example`, `//evil.example`, `/\evil.example` → `/`.
Проверка стоит и на сервере (действие входа), и на странице (в скрытое поле
и ссылку на регистрацию чужой адрес не попадает), и в ссылках из писем.

## Сессии

- **Где:** cookie `sb-<проект>-auth-token` от `@supabase/ssr`: `SameSite=Lax`,
  `Secure` в продакшен-сборке (`lib/supabase/cookie-options.ts`). Не
  httpOnly — браузерный клиент берёт из неё токен для Realtime и загрузки
  файлов; от XSS защищает CSP с nonce. В `localStorage` ничего нет.
- **Каждый запрос:** `middleware.ts` вызывает `auth.getUser()` — Auth
  проверяет токен и что сессия не отозвана — и при нужде продлевает её.
  Обновлённые или стёртые cookie переносятся и в ответ-редирект, иначе
  браузер повторял бы продление уже отозванной сессии на каждом запросе.
- **Сервер:** серверные компоненты и действия берут пользователя через
  `getUser()` (`lib/data/session.ts`, `lib/actions/actor.ts`), а не
  `getSession()`: cookie можно подделать.
- **База — последний рубеж (0043).** PostgREST проверяет у JWT подпись и
  срок, но не то, что сессия ещё есть: до 0043 токен после «выйти на всех
  устройствах» или смены пароля читал данные до часа. Теперь
  `private.current_user_id()` ищет строку `auth.sessions` по `session_id` из
  JWT; нет строки или вышел её `not_after` — для всех политик это «не
  вошёл». Проверено pgTAP (`05_auth.test.sql`) и E2E (старый токен после
  выхода везде получает пустой ответ и 401/403 на запись).
- **Истёкшая сессия:** middleware видит cookie сессии, но не пользователя —
  вход с `expired=1` и текстом «Сессия закончилась», после входа — обратно.
- **Вкладки:** экран «Ты вышел» сообщает остальным вкладкам через
  `BroadcastChannel`, и они сразу уходят на вход (`components/auth/session-sync.tsx`).
- **Аккаунт без профиля** почти невозможен (триггер в той же транзакции,
  удалить профиль в обход аккаунта нельзя), но если случился —
  `ensure_my_profile()` восстанавливает его по тем же правилам, а не роняет
  экран и не зацикливает редиректы.

### Выход

| Кнопка | Где | Что делает |
|---|---|---|
| «Выйти» | Настройки, «Вход и безопасность» | `signOut({ scope: "local" })` — только это устройство; cookie стираются, даже если Auth не ответил |
| «Выйти на всех устройствах» | «Вход и безопасность» | `signOut({ scope: "global" })` — все сессии; если Auth не ответил — так и говорим, а не делаем вид |

После выхода — `/auth/login` с подтверждением; обновление страницы и прямой
адрес ведут на вход, кнопка «Назад» не показывает закрытые экраны.

## Восстановление пароля

`/auth/forgot` (`/forgot-password`) → письмо → `/auth/reset`
(`/reset-password`) → `/auth/reset/done`.

- Ответ на запрос одинаковый для любой почты. Отказ показываем только
  тот, что не зависит от аккаунта: лимит запросов с IP и общий лимит писем.
  Раньше повторный запрос в ту же минуту выдавал «письмо уже отправлено»
  только для существующего аккаунта.
- Форма нового пароля открывается только по свежей ссылке: httpOnly-метка
  `tgt-recovery` на 15 минут, привязанная к аккаунту и выставленная, лишь
  если Auth сам недавно отправлял письмо сброса (`lib/recovery.ts`).
  Открытой сессии мало — иначе кто угодно у открытого ноутбука сменил бы
  пароль.
- Работает в том же браузере (PKCE) и на другом устройстве (token_hash,
  `/auth/confirm`).
- Форма показывает, для какого аккаунта меняется пароль, и даёт менеджеру
  паролей скрытое поле `username`.
- После смены Auth отзывает все остальные сессии, а 0043 делает это
  мгновенным и для базы. Это устройство остаётся внутри.

## «Вход и безопасность» (`/settings/security`)

- Почта для входа, дата подтверждения, дата создания аккаунта — из Auth,
  видит только владелец.
- **Смена пароля** — с текущим паролем. Supabase Auth проверяет текущий
  пароль при `updateUser` только под флагом сервера, поэтому проверка —
  отдельный вход клиентом без cookie, сессию которого мы сразу отзываем
  (`lib/supabase/auth.ts → verifyPassword`).
- **Удаление аккаунта** (`/settings/account`) — набранный ник и пароль,
  затем файлы Storage, `delete_my_account()` (каскад, DSGVO ст. 17) и выход.
- **Подбор пароля изнутри сессии** ограничен: не больше пяти проверок за
  15 минут на аккаунт (`claim_reauth_attempt()`, 0043; шестая — P0429).

## Защищённые маршруты

| Класс | Маршруты | Чем защищено |
|---|---|---|
| Публичные | `/auth/*`, `/legal/*`, `/api/health`, `/login`, `/signup`, `/register`, `/forgot-password`, `/reset-password` | `lib/public-paths.ts`; редиректы — `next.config.ts` |
| Только вошедшим | всё остальное: лента, идеи, чаты, личка, поиск, уведомления, профиль, настройки, `/api/account/export` | middleware (вход), RLS (данные), `getUser()` в действиях |
| Привилегированные | `/api/webhooks/stripe` | подпись HMAC; `service_role` только для `apply_verification_result()` |

Скрыть кнопку — не защита: каждая запись идёт в базу с JWT человека, и
отказывает RLS. Это проверяют E2E, которые ходят в `/rest/v1` мимо
приложения с настоящим токеном (`e2e-live/security.spec.ts`).

## Перечисление аккаунтов

| Где | Что сделано |
|---|---|
| вход | одна ошибка для «нет такой почты» и «неверный пароль»; «почта не подтверждена» — только при верном пароле |
| регистрация | занятая почта → тот же экран «Проверь почту» |
| сброс пароля, повторное письмо | один ответ; «письмо уже ушло» и сбой отправки маскируются |
| ник | случайный, из почты ничего не выводится |
| адресная строка | почты в адресе нет нигде |

Остаётся: сам API Supabase Auth отвечает на `/auth/v1/signup` с занятой
почтой кодом `user_already_exists`, а на повторный `/recover` — 429. Это
поведение Auth, а не приложения: закрыть его можно только CAPTCHA на
стороне Auth (ниже, «Лимиты»).

## Лимиты

| Что | Кто ограничивает | Как |
|---|---|---|
| вход, регистрация, письма, проверка ссылок | Supabase Auth | по IP; письма — раз в минуту на адрес и общий лимит проекта |
| подбор пароля изнутри сессии | база, 0043 | 5 за 15 минут на аккаунт |
| записи (сообщения, идеи, подписки…) | база, 0031 | по аккаунту |

**Требование для продакшена.** Вход идёт через server actions, поэтому
для Auth все пользователи приходят с адресов Vercel. Без пересылки IP один
перебор паролей исчерпает лимит входа для всех. Supabase решает это
заголовком `Sb-Forwarded-For`, который `lib/supabase/auth.ts` ставит, когда:

1. Supabase → Authentication → Rate Limits → **IP Address Forwarding** включён;
2. в Vercel заданы `SUPABASE_SECRET_KEY` (новый ключ `sb_secret_…`, старый
   `service_role` не подходит) и `SUPABASE_AUTH_IP_FORWARDING=true`.

Секретный ключ в этом клиенте используется только для шести методов Auth;
`.from()` и `.auth.admin` из модуля не выходят. Без этих настроек всё
работает с публичным ключом, как раньше, — но лимит общий. В приложении
нет счётчика попыток в памяти: на serverless у каждого экземпляра он свой и
ничего не защищает.

Рекомендовано дальше: CAPTCHA Supabase (Turnstile или hCaptcha) на
регистрацию, вход и сброс — она закрывает и перебор, и перечисление на
уровне самого Auth.

## Ошибки и журнал

`lib/auth/errors.ts` переводит ответ Auth в категорию (`invalid_credentials`,
`email_frequency`, `rate_limited`, `link_invalid`…) и текст по-русски. Текст
сервера человеку не показывается. В журнал (`lib/auth/report.ts`) — одна
строка JSON: операция, категория, код и статус Auth, маршрут, `x-vercel-id`.
Без почты, пароля, токенов и IP. Неверный пароль и «письмо уже ушло» не
пишутся — это обычная жизнь формы.

## Формы

- Поля проверяются в браузере теми же правилами, что на сервере: ошибка у
  поля при уходе с него и при отправке, фокус — на первое поле с ошибкой,
  общая ошибка — `role="alert"` с фокусом. Правка поля убирает его ошибку.
- Кнопка отправки выключена, пока идёт запрос: двойной отправки нет.
- «Показать пароль» — переключатель с `aria-pressed`; перед отправкой
  пароль снова скрывается (менеджеры паролей смотрят на `type=password`).
- `autocomplete`: `email`, `current-password`, `new-password`; на формах
  смены и сброса — скрытое `username` с почтой.
- После ответа сервера React сбрасывает форму: почта возвращается из
  состояния, пароли — никогда, согласие с условиями сохраняется.

## Будущее: регистрация только для вузов

Сейчас (MVP) `private.registration_policy.mode = 'open'` (0044). Решает,
можно ли создать аккаунт, одна функция — `private.signup_allowed(address)`;
её вызывает триггер регистрации (отказ = аккаунта нет вовсе, даже при
прямом вызове API) и форма через `public.signup_allowed()` (понятный
отказ до похода в Auth).

1. **Вернуть «только почта вуза»** — миграция
   `update private.registration_policy set mode = 'university'`. Всё
   остальное уже работает: домены `universities`, `email_allowlist`, текст
   отказа в форме.
2. **Одобренные участники** — новый режим без замены Auth и профиля:

   ```sql
   create table public.organizations (id uuid primary key, …);
   create table private.approved_members (
     organization_id uuid references public.organizations,
     email text,           -- или подтверждённый внешний идентификатор
     approved_at timestamptz, …
   );
   -- registration_policy_mode: + 'approved'
   -- private.signup_allowed(): when 'approved' then exists (…approved_members…)
   -- private.create_profile(): вуз/организация — из approved_members
   ```

   `auth.users.id`, `public.users`, `current_user_id()`, политики и все
   экраны не меняются. Заявку («хочу в To Get There») удобно сделать
   отдельной таблицей и экраном до регистрации; ответ формы заявки должен
   быть одинаковым, есть ли адрес в списке, — иначе это новый канал
   перечисления.
3. **Существующие аккаунты без вуза** при закрытии регистрации остаются:
   решите заранее, переводятся ли они в «одобренные» или получают
   ограниченный доступ. Это продуктовое решение, а не техническое.
