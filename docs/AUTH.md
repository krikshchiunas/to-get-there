# Вход и аккаунт

Почта и пароль через Supabase Auth. Регистрация открыта любой почте (MVP,
0043); проверка вуза — потом, когда появятся партнёрства, и без замены
Supabase Auth (см. последний раздел).

## Архитектура

```
Браузер ── форма ──▶ серверное действие (app/auth/actions.ts)
                         │  правила полей, лимит попыток, журнал
                         ▼
                    Supabase Auth (GoTrue)  ── письма ──▶ почта
                         │  сессия в cookie (@supabase/ssr)
                         ▼
                    auth.users.id  ── то, что подтверждает JWT (auth.uid())
                         │  1:1, users.auth_user_id unique, on delete cascade
                         ▼
                    public.users  ── профиль (ник, вуз, приватность)
                         │  private.current_user_id() в каждой политике
                         ▼
                    данные приложения под RLS
```

**Идентичность безопасности — `auth.users.id`.** Его подтверждает подпись
JWT, сервер получает его только из `supabase.auth.getUser()` (проверка
токена на стороне Supabase, а не `getSession()`, которая верит cookie).
У профиля свой ключ `users.id`, но связь с аккаунтом — уникальный
`users.auth_user_id`, и найти профиль можно только через неё:
`private.current_user_id()` в политиках, `lib/auth/profile.ts` в
приложении. Клиент id профиля не присылает и выбрать его не может;
`auth_user_id` нет в праве на запись, а триггер (0007) его замораживает.

Почему ключ профиля не равен `auth.users.id`: так схема жила до входа
(сид и демо — профили без аккаунта), а все внешние ключи ссылаются на
`users.id`. Связь один к одному с каскадным удалением делает это
эквивалентным для безопасности, а переписывать ключи всей схемы ради
формы — риск без выигрыша.

## Маршруты

| Открыто без входа | Только со входом |
|---|---|
| `/auth/*` (вход, регистрация, письма, сброс), `/legal/*`, `/api/health`, вебхук Stripe (подпись) | всё остальное: лента, идеи, чаты, личка, профили, поиск, уведомления, настройки, выгрузка данных |

Middleware (`middleware.ts`) уводит без сессии на `/auth/login?next=…`.
Это удобство, а не защита: каждое чтение и запись идут через клиент с
сессией пользователя, и решает RLS. Вошедшего `/auth/login` и
`/auth/signup` возвращают на главную.

## Потоки

**Регистрация** (`signUp`). Почта, пароль, повтор; проверка в браузере и на
сервере (`lib/auth/credentials.ts`). Лимит попыток. GoTrue создаёт
`auth.users`, триггер в той же транзакции — профиль
(`private.create_profile_for`). Занятый адрес отвечает так же, как новый.
Адрес для экрана «Проверь почту» — в httpOnly cookie на час, не в строке
запроса.

**Подтверждение почты.** Два пути:
- `/auth/callback?code=…` — PKCE, ссылка по умолчанию. Работает в том же
  браузере, где регистрировались.
- `/auth/confirm?token_hash=…&type=email` — на любом устройстве. Нужен
  шаблон письма (раздел «Настройки Supabase»). Страница ничего не меняет
  сама: вход — по кнопке, серверным действием. Почтовые сканеры
  (Microsoft 365 Safe Links и подобные) открывают ссылки из писем для
  проверки; будь вход на GET, одноразовый токен сгорал бы до человека. И
  чужую ссылку нельзя «скормить» так, чтобы человек молча оказался в
  чужом аккаунте.

Устаревшая, использованная или поддельная ссылка ведёт на
`/auth/login?error=link` с объяснением. Повторное письмо — форма на
«Проверь почту» и ссылка в ошибке входа «почта не подтверждена».

**Вход** (`signIn`). Лимит попыток, `signInWithPassword`, затем
`safeNext(next)`: только путь внутри приложения — без схемы, без `//`,
без обратного слэша и управляющих символов, без `/auth`
(`lib/safe-next.ts`). Чужой адрес ведёт на главную.

**Сессия.** Cookie `@supabase/ssr` (`lib/supabase/cookies.ts`): `Secure` в
продакшене, `SameSite=Lax`, без `Domain`. Не `HttpOnly` — браузерному
клиенту нужен токен для realtime; защита от кражи скриптом — CSP с nonce.
Middleware продлевает токен на каждом запросе. `localStorage` для входа не
используется.

**Выход** (`signOut`). `scope: "local"`: сессия этого устройства
отзывается в Supabase (refresh-токен больше не обменять, скопированные
cookie не пускают), cookie стираются, редирект на вход. Если Supabase не
ответил — cookie сессии стираются вручную.

**Сброс пароля.** «Забыли пароль?» → письмо (ответ одинаковый для любой
почты) → `/auth/callback?type=recovery` (PKCE) или
`/auth/confirm?type=recovery` (token_hash) → httpOnly-метка на 15 минут,
только если Supabase сам отправлял письмо сброса этому аккаунту за
последний час (`recovery_sent_at`) → форма нового пароля → `updateUser`
→ остальные сессии аккаунта отзываются → `/auth/reset/done`. Токены сброса
приложение не хранит и не пишет в журнал.

**Профиль.** Создаётся в транзакции регистрации. Если строки нет (удалили
вручную, старый аккаунт), `lib/auth/profile.ts` вызывает
`ensure_my_profile()` — та же функция; повтор безопасен. Удалить профиль
можно только вместе с аккаунтом (`delete_my_account()`).

## Меры защиты

| Угроза | Мера |
|---|---|
| Перебор паролей | лимит попыток в Postgres: 10 на почту с одного адреса за 15 мин, 50 на почту за час, 60 с адреса за 10 мин |
| Спам письмами | 5 писем сброса и 5 повторных подтверждений на почту в час, 20 с адреса |
| «Есть ли аккаунт?» | одинаковые ответы регистрации, сброса и повторного письма; текст «Проверь почту» не утверждает, что письмо ушло |
| Открытый редирект | `safeNext()`; e2e-live проверяет `https://…`, `//…`, `/\…`, `javascript:` |
| Смена пароля с чужой сессии | только по свежей ссылке из письма; метка привязана к аккаунту |
| Вор остался внутри после сброса | `signOut({ scope: "others" })` после смены пароля |
| Украденные cookie после выхода | сессия отозвана в Supabase; проверяется в e2e-live |
| Подмена идентичности | сервер берёт аккаунт только из проверенного JWT; профиль — по `auth_user_id` |
| Повышение прав | вуз, `auth_user_id`, `is_verified`, авторство, роли модераторов — вне прав на запись и под RLS (pgTAP 05) |
| Вход без профиля | самовосстановление; иначе — страница ошибки, а не цикл редиректов |
| Утечка в журнал | запись собирается только из разрешённых полей; маршрут без строки запроса |
| Сообщения Supabase на экране | категория → свой текст (`lib/auth/errors.ts`) |
| Session fixation | сессию выдаёт только Supabase после проверки пароля или ссылки; приложение не принимает id сессии от клиента |
| Login CSRF и сканеры почты по ссылке с token_hash | `/auth/confirm` на GET ничего не меняет; вход — по кнопке (POST) |

## Лимиты попыток — как устроены и где предел

`public.auth_attempt(operation, ip_key, email_key)` (0043) считает попытки в
`private.auth_attempts` и отвечает «можно» или «через N секунд». Пределы — в
функции. Ключи — HMAC-SHA256 адреса и почты на серверном ключе:
журнал попыток не хранит ни того, ни другого. Вызывать может только
`service_role` — сервер приложения (`lib/auth/rate-limit.ts`).

Честно о пределах:
- **Без `SUPABASE_SECRET_KEY` на сервере лимит не работает**: попытка
  пропускается, в журнал — `auth_rate_limit_unavailable`. Запирать всех
  из-за сбоя лимитера хуже. Тогда остаются только лимиты GoTrue.
- **Лимиты GoTrue считаются по IP сервера**, а не человека: запросы к нему
  идут с Vercel. Это общий потолок на всех, а не защита от одного.
- **Адрес клиента достоверен только на Vercel** (`x-vercel-forwarded-for`).
  За другим прокси заголовки может прислать сам клиент; лимиты по почте
  от адреса не зависят.
- Попытки считаются все, а не только неудачные; блокировка по почте с
  чужих адресов возможна (50 в час) — это цена защиты от распределённого
  перебора.

## Журнал

Одна строка JSON на событие (`lib/auth/log.ts`):
`{"evt":"auth","ts":…,"op":"sign_in","outcome":"failure","category":"invalid_credentials","route":"/auth/login","requestId":"fra1::…"}`.
Операции: `sign_in`, `sign_up`, `sign_out`, `password_reset_request`,
`password_update`, `resend_confirmation`, `email_link`, `profile_repair`.
Почты, адресов, паролей, токенов и ссылок из писем в записи нет.

Остаётся за пределами приложения: журнал запросов Vercel пишет путь со
строкой запроса, то есть одноразовые `code` и `token_hash` из ссылок
писем. Они действуют один раз и недолго, PKCE-код без cookie браузера
бесполезен, а доступ к журналу — только у владельца проекта.

## Настройки Supabase (прод, руками)

- **Authentication → URL Configuration**: Site URL —
  `https://to-get-there-mu.vercel.app`; Redirect URLs —
  `https://to-get-there-mu.vercel.app/**`.
- **Email Templates → Confirm signup**: ссылка
  `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`.
- **Email Templates → Reset Password**: ссылка
  `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery`.
- **SMTP**: свой провайдер — встроенная почта шлёт только участникам
  команды проекта.
- **Vercel → Environment Variables**: `SUPABASE_SECRET_KEY` (без
  `NEXT_PUBLIC_`) — для лимитов попыток.
- Пароль: минимальная длина в Supabase — 8 (как в приложении);
  «Prevent use of leaked passwords» — на платном тарифе.

Локально всё это уже в `supabase/config.toml`: письма — в Mailpit
(`http://127.0.0.1:54324`), лимиты GoTrue подняты для e2e-live.

## Выкатка 0043

Порядок — сначала приложение, потом миграция (`docs/STAGING.md`):
1. Приложение умеет профиль без вуза и не зависит от новых функций:
   без `auth_attempt` лимитер пропускает с предупреждением, без
   `ensure_my_profile` пропавший профиль даёт ошибку, как раньше.
2. Миграция только расширяет схему: столбцы становятся необязательными,
   функции и таблица добавляются, триггер перестаёт отказывать.

## Проверка вуза — потом, без замены входа

Сейчас вуз — подсказка по домену подтверждённой почты. Когда появятся
партнёрства, правило «кто может зарегистрироваться» встаёт **до создания
аккаунта**, на стороне сервера и базы:

```
форма регистрации
      ↓
проверка права (организация, приглашение, домен)   ← сюда
      ↓
Supabase Auth (signUp)  →  auth.users.id
      ↓
private.create_profile_for  →  public.users
      ↓
organization_members (членство, роль, статус)
```

Где именно:
- **Перед `auth.users`** — Supabase Auth Hook «Before User Created»
  (функция Postgres или HTTP): отказ до создания аккаунта, единственное
  место, которое не обойти прямым вызовом GoTrue. Альтернатива на время —
  проверка в `signUp` (сервер) плюс отказ в триггере, как делал 0013.
- **Членство** — новые таблицы `organizations`, `organization_members`,
  `invites` вместо одного `users.university_id`. Заполнять их будет
  `private.create_profile_for` (уже единая точка создания профиля).
- **Права** — `private.my_university_id()` (0042) превращается в
  множество организаций зрителя; политики «мой вуз» меняются в одной
  функции, а не в каждой таблице.
- Supabase Auth, сессии, письма, восстановление, `auth.users.id` как
  идентичность — не меняются.
