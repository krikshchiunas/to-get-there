# База данных

Postgres 15 в Supabase. Схема живёт в `supabase/migrations/` и применяется
строго по порядку, с 0001 по 0009, после чего выполняется `supabase/seed.sql`.
Ручных шагов между файлами нет.

| Файл | Что внутри |
| --- | --- |
| `0001_extensions.sql` | схемы расширений, `pgcrypto`, `pg_trgm`, соглашения всего набора |
| `0002_reference.sql` | перечисления (`chat_access`, `geo_mode`, `notification_type`), университеты, категории |
| `0003_users.sql` | профили, отвязанные от авторизации, `current_user_id()` |
| `0004_posts.sql` | идеи, состав чата, модераторы |
| `0005_chat.sql` | сообщения, голосования, голоса, личные сообщения |
| `0006_social.sql` | подписки и уведомления |
| `0007_views_functions.sql` | функции правил, представления, триггеры, индексы |
| `0008_rls.sql` | RLS и права на колонки |
| `0009_realtime_storage.sql` | публикация realtime и бакеты файлов |
| `seed.sql` | тот же набор данных, что в `lib/mock` |
| `later/auth_bridge.sql` | регистрация. **Не применять сейчас** — это шестой этап |

Соглашения, которые держат все файлы: первичный ключ — `uuid` с
`gen_random_uuid()`, время — `timestamptz`, расширения живут в схеме
`extensions`, у каждой функции `set search_path = ''` и полные имена внутри.

## 1. Таблицы

### `universities`
Восемь университетов. `domain` — почтовый домен, по которому на шестом этапе
проверяется университетская почта. `short_name` («TU Berlin») показывается на
карточках, где не влезает полное название. Справочник: читают все, пишут
только миграции и service role.

### `categories`
Двадцать категорий. Восемь с `is_main = true` предлагаются сразу на экране
«Новая идея» и в фильтрах, остальные — за кнопкой «Другое». `icon` — ключ из
`IconName` (`lib/types.ts`), текстом, чтобы набор иконок мог расти без
миграции.

### `users`
Профиль. Главное решение всей схемы: `users.id` — свой uuid, на него
ссылаются все остальные таблицы, а `auth_user_id` — необязательная ссылка на
`auth.users`. Поэтому база работает, когда авторизации ещё нет вообще: у всех
посеянных людей `auth_user_id = null`, и войти как они нельзя.

- `nickname` — нижний регистр, уникален, 3–24 символа `[a-z0-9._]`. Это
  ровно сегмент адреса `/u/<nickname>`.
- `interests`, `goals` — массивы текста, элементы проверяет
  `is_tag_array()`.
- `is_verified` — только подтверждённая личность. **Не даёт никаких прав** и
  не записывается самим пользователем: колонки нет в гранте на UPDATE, а
  триггер `users_guard_verification` возвращает прежнее значение.
- `privacy_settings`, `notification_settings` — jsonb фиксированной формы,
  форму держат CHECK-ограничения; опечатка в ключе падает на вставке, а не на
  экране.

### `posts`
Идея: время (`date_start`), место (`geo_*`) и число мест
(`max_participants`, `null` — без ограничения). `is_closed` — автор закрыл
набор. `chat_access` — кто может зайти в чат. `university_id` не присылает
клиент: его ставит триггер по профилю автора, потому что идея принадлежит
университету того, кто её собирает.

### `post_participants`
Состав чата идеи. «Участник этой идеи» — это ровно «есть строка здесь»,
включая автора: его строку добавляет триггер при создании идеи. Эти же строки
считает счётчик мест.

### `post_moderators`
Права модератора, выданные поимённо: `can_post_media`, `can_pin`, `can_poll`,
`can_kick`. Автор держит все четыре неявно и в этой таблице не появляется
никогда.

### `messages`
Групповой чат одной идеи. `is_pinned` — не больше одного закрепления на идею:
это гарантирует частичный уникальный индекс, а триггер
`messages_single_pin` снимает прежнее закрепление, чтобы новое не падало с
ошибкой.

### `polls`, `poll_votes`
Голосование в чате. `options` — массив `{ "label": "…" }` из двух–шести
элементов, он выровнен по индексу с `poll_votes.option_index` и **никогда не
переупорядочивается**: поэтому у `polls` нет ни политики, ни гранта на
UPDATE. Один голос на человека (уникальность по `poll_id, user_id`),
«передумал» — это UPDATE своей строки. Результаты видны всем, кто видит само
голосование.

### `direct_messages`
Личная переписка. `conversation_key` — генерируемая колонка
`least(sender,receiver) || ':' || greatest(sender,receiver)`, одна и та же для
обоих направлений, так что ветка читается одним диапазонным сканом индекса.

### `follows`
Подписка, односторонняя. Взаимная пара — это дружба, и она нигде не хранится
(см. ниже).

### `notifications`
Уведомления. Строки пишут только триггеры из 0007: гранта и политики на
INSERT для `authenticated` нет, иначе клиент мог бы подделать «кто-то
присоединился». `payload` денормализован (ник, заголовок идеи, превью
сообщения), поэтому список рисуется одним запросом и остаётся читаемым, даже
когда идею удалили. Получатель только переключает `is_read` или удаляет
строку.

### `app_flags`
Одна строка настройки. `open_read = true` — база в режиме разработки: каждая
политика на SELECT начинается с `public.open_read() or …`, потому что на
четвёртом и пятом этапах авторизации ещё нет и `auth.uid()` всегда `null`. На
запись флаг не влияет никогда.

## 2. Функции правил (0007)

Каждое правило продукта описано в двух местах, и они обязаны совпадать:

| TypeScript | Postgres |
| --- | --- |
| `isInFeed(post, now)` | `public.active_posts`, `post_cards.in_feed` |
| `isFriend(user)` | `are_friends(a, b)` |
| `canEnterChat(post)` | `can_enter_post_chat(post, member)` |
| `canMessage(user)` | `can_message_user(target, sender)` |
| `canSeeProfile(user)` | `can_see_profile(target, viewer)` |
| `canSeeInterests(user)` | `can_see_interests(target, viewer)` |
| `roleOf(postId, userId)` | `post_role(post, member)` |
| `seatsLeft` / `isFull` | `participant_count(post)`, `post_cards.seats_left` |

Плюс служебные: `current_user_id()` (0003) — единственный источник личности
для политик; `follows_user`, `shares_post_with`, `post_author_id`,
`is_post_author`, `is_post_member`, `can_moderate`, `can_join_post`,
`poll_post_id`, `audience_allows`, `notification_enabled`, `try_uuid`,
`open_read`.

Все они `security definer`. Это не удобство, а необходимость: политика на
`public.users`, которая сама читала бы `public.users` под RLS, зациклилась бы.
Функция-definer читает как владелец таблицы и разрывает цикл — поэтому внутри
такой функции не должно происходить ничего, кроме ответа на вопрос из её
имени.

### Представления

- **`active_posts`** — идеи, которые сейчас в ленте: `not is_closed` и
  `date_start + interval '1 hour' > now()`. `security_invoker = true`, то есть
  чтение представления применяет политику читающего на `posts`.
- **`post_cards`** — всё, что нужно карточке ленты: идея + ник, аватар,
  галочка и факультет автора + университет + категория + число участников +
  `seats_left` + `in_feed`. Читается как владелец
  (`security_invoker = false`) — осознанно: профиль с настройкой
  «университет» или «друзья» не виден большинству по политике на `users`, и
  представление-invoker молча выкидывало бы идеи таких авторов из ленты. Блок
  автора на карточке по определению публичен («достаточно, чтобы
  нарисовать, ничего приватного» — `docs/ui-contract.md`), а условие доступа
  к `posts` повторено в самом представлении, чтобы его нельзя было обойти.
  **Добавлять в это представление новые колонки из `users` нельзя.**

### Триггеры

| Триггер | Когда | Что делает |
| --- | --- | --- |
| `posts_set_university` | before insert/update `posts` | ставит `university_id` по автору, замораживает `author_id` и `created_at` |
| `posts_add_author_participant` | after insert `posts` | сажает автора в состав чата |
| `users_guard_verification` | before insert/update `users` | никто не выставляет себе `is_verified`, `auth_user_id` и `created_at` тоже не двигаются |
| `messages_single_pin` | before insert/update `messages` | снимает прежнее закрепление в этой идее |
| `poll_votes_check_option` | before insert/update `poll_votes` | `option_index` не выходит за число вариантов |
| `post_participants_notify_author` | after insert | уведомление автору о новом участнике |
| `messages_notify_participants` | after insert | уведомление всем остальным участникам идеи |
| `follows_notify_target` | after insert | уведомление о новом подписчике |
| `posts_notify_followers` | after insert `posts` | новая идея от того, на кого подписан |

Каждый уведомляющий триггер сначала спрашивает `notification_enabled()`:
выключенное уведомление не создаётся, а не создаётся и скрывается.

`event_reminder` триггера не имеет: он зависит от часов, а не от записи. Это
работа планировщика (`pg_cron` раз в несколько минут, по
`event_reminder_1h` и `event_reminder_30m`), и она записана в
`docs/ROADMAP.md`, а не выдумана в схеме.

## 3. Правило ленты

Идея уходит из **обеих** вкладок, когда автор закрыл набор (`is_closed`) или
прошёл час после `date_start`. Чат при этом остаётся доступным всем, кто в нём
был, — из списка чатов и из профиля автора.

Это правило существует в трёх местах, и они обязаны совпадать:
`isInFeed(post, now)` в `lib/format.ts`, представление `active_posts` и
колонка `in_feed` в `post_cards`.

Сортировка: **обе вкладки строго хронологические, `order by date_start asc`** —
ближайшее первым. Никакого ранжирования, никакого буста по свежести, никаких
закреплённых мест в ленте.

```sql
-- Подписки
select c.* from public.post_cards c
join public.follows f on f.following_id = c.author_id
where f.follower_id = public.current_user_id()
  and c.in_feed
order by c.date_start;

-- Университет
select c.* from public.post_cards c
where c.university_id = (select u.university_id from public.users u where u.id = public.current_user_id())
  and c.in_feed
order by c.date_start;
```

## 4. Правило дружбы

**Друзья — это взаимная подписка, и ничего больше.** Дружба нигде не
хранится, она всегда выводится из двух строк `follows`, поэтому отписка
расторгает её немедленно — вместе со всеми уровнями приватности, которые на
ней держатся: `who_can_message = 'friends'` и `chat_access = 'friends'`.

`are_friends(a, b)` = `follows_user(a, b) and follows_user(b, a)`.

## 5. Политики прозой (0008)

Два слоя делают разную работу. **Гранты** решают, до каких колонок роль
дотягивается вообще: так `users.is_verified` становится незаписываемым, а
`authenticated` может переключить `messages.is_pinned`, не имея возможности
переписать чужое сообщение. **Политики** решают, какие строки видны и какие
можно менять.

У каждой политики на SELECT форма `public.open_read() or <настоящее правило>`.
В политиках на INSERT, UPDATE и DELETE `open_read()` не встречается ни разу:
записи всегда нужен вошедший пользователь. `service_role` обходит RLS целиком
(роль создана с `bypassrls`), `postgres` — владелец таблиц и тоже вне RLS,
поэтому сид и инструменты модерации работают без чёрных ходов в политиках.

### Справочники
`universities`, `categories`, `app_flags` — читают все, включая анонимов.
Писать может только service role и миграции.

### `users`
**Чтение.** Своя строка — всегда. Чужая — если `who_can_see_profile`
разрешает (`everyone`, `university` — тот же университет, `friends` —
взаимная подписка) **или** если вы участники одной идеи. Второе условие —
осознанное расширение: чат, в котором участники рисуются пустыми строками,
сломан.

**Приватность интересов** (`who_can_see_interests`) в RLS не выражается:
политика скрывает строки, а не колонки. Её применяет экран профиля и слой
чтения через `can_see_interests()`. Если потребуется жёсткая гарантия —
интересы придётся вынести в отдельную таблицу или отдавать через
представление; сейчас это сознательный компромисс.

**Запись.** Только своя строка, только колонки профиля и настроек. `id`,
`auth_user_id`, `university_id`, `created_at` и `is_verified` в гранте
отсутствуют: смена университета меняет ленту, в которую попадают твои идеи, —
это обращение в поддержку, а не переключатель в настройках. Политики на
INSERT нет вообще: профили создаёт мост авторизации
(`supabase/later/auth_bridge.sql`) и сид. Удалить можно только себя.

### `posts`
**Чтение** — любая идея любому вошедшему: на этом стоит вкладка
«Университет» и поиск. Закрыт только чат за идеей.
**Создание** — `author_id` обязан быть тобой.
**Изменение и удаление** — только автор. «Закрыть набор» — это UPDATE
`is_closed`, то есть та же политика и делает закрытие набора действием
автора.

### `post_participants`
**Чтение** — как сама идея: карточка показывает стопку аватаров и счётчик
мест, а это те же строки.
**«Присоединиться»** — вставить можно только строку про себя и только пока
проходит `can_join_post()`: доступ в чат разрешён, набор открыт, место
свободно, тебя там ещё нет. Добавить кого-то другого нельзя никому.
**Выйти** — удалить свою строку. **«Удалить из чата»** — то же удаление,
выполненное автором или модератором с `can_kick`, причём автора идеи из его
собственной идеи удалить нельзя. UPDATE отсутствует: `joined_at` — факт.

### `post_moderators`
Читают все вошедшие (роли показаны в списке участников). Назначать, менять
права и снимать может **только автор**, и только тех, кто уже в чате. Себя
автор модератором сделать не может — он и так держит все четыре права.

### `messages`
**Чтение** — ровно `chat_access`: «Все» пускает любого вошедшего, «Только
подписчики» и «Только друзья» — нет. Кто уже в чате, читает его всегда,
включая время после закрытия набора и после самой встречи.
**Запись** — нужно быть участником, а не просто иметь доступ: сначала
вступаешь, потом говоришь. Вложение требует права `can_post_media` (у автора
есть всегда, у модератора — по правам).
**«Закрепить» / «Открепить»** — единственная изменяемая колонка `is_pinned`,
и менять её может автор или модератор с `can_pin`.
**Удаление** — своё сообщение или любое, если ты автор идеи.

### `polls`, `poll_votes`
Видно тем, кто может зайти в чат. Создать голосование может автор или
модератор с `can_poll`. Удалить — создатель или автор идеи. Изменять
голосование нельзя (варианты выровнены по индексу с голосами). Голос —
только свой: вставить, переставить `option_index`, удалить.

### `direct_messages`
Читают ровно двое участников переписки. Отправить можно, если
`who_can_message` получателя разрешает: `everyone`, `friends` (взаимная
подписка) или `nobody`. Отписка мгновенно закрывает переписку для
получателя с настройкой `friends`. Удалить можно только своё отправленное,
редактировать — нельзя.

### `follows`
Списки «Подписчики» и «Подписки» открыты. Подписаться можно только от своего
имени, отписаться — только от своей подписки. Удалить подписчика продукт не
умеет, поэтому и политики такой нет.

### `notifications`
Видишь только свои. Единственное действие — отметить прочитанным или
удалить. INSERT нет ни в гранте, ни в политике: пишут триггеры.

## 6. Realtime и файлы (0009)

В публикации `supabase_realtime` пять таблиц: `messages`,
`direct_messages`, `poll_votes`, `post_participants`, `notifications`.
Подписка отдаёт только те строки, которые подписчик имеет право читать по
политикам выше. `posts` и `users` в публикацию намеренно не входят: лента —
расписание, а не бегущая строка, и карточка, которая перестраивается под
пальцем, хуже карточки, которой минута от роду. У `post_participants` и
`poll_votes` стоит `replica identity full`, потому что UI реагирует на их
удаления (человека удалили из чата, голос забрали).

Три бакета:

| Бакет | Доступ | Путь | Лимит |
| --- | --- | --- | --- |
| `avatars` | чтение публичное, запись только владельцу | `<users.id>/<файл>` | 2 МиБ |
| `post-media` | читают те, кто может зайти в чат идеи; загружают автор и модератор с `can_post_media` | `<posts.id>/<файл>` | 10 МиБ |
| `verification` | только владелец и service role | `<users.id>/<файл>` | 10 МиБ |

Первый сегмент пути — всегда владеющая сущность, его и проверяют политики
через `storage.foldername(name)`. Непарсящийся сегмент превращается в `null`
функцией `try_uuid()`, и доступ закрывается, а не падает с ошибкой. У
`verification` нет политики на UPDATE: новая попытка — новый файл, чтобы
проверенный документ нельзя было подменить под проверкой.

## 7. Как это применить

### Локально

```bash
# один раз: CLI
brew install supabase/tap/supabase        # или npx supabase@latest

# supabase/config.toml уже лежит в репозитории, поэтому этот шаг не нужен.
# Он здесь для пустого проекта; на существующем config.toml команда
# откажется работать без --force, и это правильное поведение:
# перезаписывать наш конфиг нельзя.
# supabase init

# поднять локальный стек (Postgres, API, Studio, почтовый ловец)
supabase start

# применить 0001-0009 с нуля и выполнить seed.sql
supabase db reset

# ключи и адреса для .env.local
supabase status
```

`supabase start` печатает `API URL` и `anon key` — это
`NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` в `.env.local`.
Studio на `http://127.0.0.1:54323`.

После `db reset` последний запрос `seed.sql` печатает таблицу с количествами.
Строка «в ленте» не должна быть нулём — в этом весь смысл относительного
времени в сиде.

### В облачный проект

```bash
# создать проект на supabase.com, затем
supabase login
supabase link --project-ref <ref>        # ref из адреса дашборда

# показать, что поедет, и поехать
supabase db diff --linked --schema public   # необязательно, для проверки
supabase db push

# сид в облако — вручную, он не часть db push. Строка подключения лежит в
# дашборде: Project Settings → Database → Connection string → URI
psql "postgresql://postgres:<пароль>@db.<ref>.supabase.co:5432/postgres" -f supabase/seed.sql
# или: открыть supabase/seed.sql в SQL Editor дашборда и выполнить целиком
```

`db push` применяет только те файлы из `supabase/migrations`, которых нет в
таблице истории на сервере, и в порядке имён — поэтому номера 0001…0009 и
важны.

`seed.sql` должен выполняться **одной сессией** (`psql -f`, `supabase db
reset` или одна вставка в SQL Editor): два помощника для относительного
времени живут в `pg_temp` и исчезают вместе с соединением.

### Типы для TypeScript

```bash
npm run db:types     # supabase gen types typescript --local > lib/database.types.ts
```

До этого клиенты в `lib/supabase/` нетипизированные, а контрактом остаются
строковые типы из `lib/types.ts` — они повторяют схему колонка в колонку.

### Переключение в строгий режим (шестой этап)

```sql
-- 1. мост авторизации
\i supabase/later/auth_bridge.sql

-- 2. выключить режим разработки
update public.app_flags set open_read = false, updated_at = now();
```

До второй команды база отдаёт чтение анонимному ключу. После — каждая
политика требует вошедшего пользователя, и приложение без экрана входа
покажет пустые экраны. Это ожидаемо и является признаком того, что
переключение сработало.

## 8. Что осталось снаружи

- **`event_reminder`** — нужен планировщик (`pg_cron`), триггером не
  делается.
- **`who_can_see_interests`** на уровне RLS — политика скрывает строки, а не
  колонки; сейчас это правило слоя чтения.
- **`visible_in_search`** — фильтр запроса, а не политика: профиль, скрытый
  из поиска, должен остаться видимым в чатах, в которых участвует. Под него
  есть частичный индекс `users_searchable_idx` (0003).
- **Гонка за последнее место** — `can_join_post()` считает участников в
  момент вставки, но ограничения «не больше `max_participants` строк» в базе
  нет: два одновременных «Присоединиться» на одно место пройдут оба. Если это
  станет важно, нужен либо `serializable`-транзакция, либо счётчик на `posts`
  с проверкой в триггере.
- **Непрочитанные личные сообщения** — закрыто миграцией `0010_direct_message_reads.sql`.
  Ранее: — `unread_count` в
  `ConversationView` пока считается в моках. В базе для этого нужна либо
  колонка `read_at` на `direct_messages`, либо таблица «прочитано до» на
  пару; решение не принято, поэтому в схеме его нет.

## Перед запуском: база сейчас открыта на чтение

Пока нет авторизации, `app_flags.open_read = true`, и политики SELECT
пропускают любого, у кого есть публикуемый ключ. Это сделано намеренно,
чтобы экраны работали до появления регистрации, и это **недопустимо на
боевом запуске**.

Что выполнить на финальном этапе — в `supabase/later/go_live_checklist.sql`:
закрыть `open_read`, отозвать у роли `anon` доступ к функциям-помощникам и
к чтению таблиц. Там же проверка, которая должна вернуть ноль.

Советник Supabase (Advisors → Security) показывает это как
`security_definer_view` на `post_cards` и `direct_conversations` — оба
представления читают межпользовательские данные осознанно и фильтруют по
`current_user_id()`; после закрытия `open_read` они перестают отдавать
что-либо без сессии.
